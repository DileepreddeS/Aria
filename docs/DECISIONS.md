# Decisions log

Format: date — decision — why — (revisit when)

- 2026-10-07 — Rebuild ARIA from scratch in a new repo; v1 kept as reference only — v1 architecture (single loop, keyword-injection rewriter, job boards) doesn't fit the product. Starting clean gives full understanding and control.
- 2026-10-07 — ARIA is built as a product for many job seekers; founder is user #1 — every design choice must work multi-tenant.
- 2026-10-07 — Hybrid architecture: cloud "brain" + local Runner doing browser work on the user's device — sessions and logins never leave the device; applications genuinely come from the user's browser and IP; removes central credential and cookie risk.
- 2026-10-07 — Browser stack: Playwright for control + raw CDP for perception (AX tree, DOMSnapshot, network, screenshots). No Puppeteer, Selenium or custom Chromium — CDP already provides all page information; more libraries add bugs, not information.
- 2026-10-07 — Workflows: explicit state machines; LangGraph with Postgres checkpoints for agent graphs; Postgres SKIP LOCKED queue between services. LLMs act inside states; code controls transitions.
- 2026-10-07 — Modular monolith + three isolated components (Runner, Credential Broker, LLM Gateway) instead of microservices — security isolation where it matters without operational sprawl.
- 2026-10-07 — Resume Engine is a standalone package: JD Parser → Requirement Normalizer → Candidate Graph → Evidence Matcher → Composer (plan, write) → ATS / Truth / Recruiter / Layout validators → PDF.
- 2026-10-07 — Job-type policies (no sponsorship, citizenship/clearance, years, staffing) are user preferences (Skip / Apply anyway / Ask me), not hard-coded skips. Form answers are always truthful regardless.
- 2026-10-07 — No CAPTCHA solving or anti-bot evasion. Users solve CAPTCHAs via the Liaison. Human pacing and the user's own browser instead.
- 2026-10-07 — LinkedIn and Indeed: discovery only, no automated applying (terms of service, account-ban risk).
- 2026-10-07 — Email intake defaults to a forwarding rule to a per-user ARIA inbox — avoids restricted Gmail scopes and their annual security assessment. (Revisit at beta.)
- 2026-10-07 — Local embeddings and NLI models for matching and truth checks — keeps candidate profiles away from third-party providers; reuses SI-RAG NLI verification.
- 2026-10-07 — PDF rendering via HTML/CSS → Chromium print-to-PDF, not docx2pdf — cross-platform, no MS Word dependency, ATS-friendly text layer.
- 2026-10-07 — Product name "ARIA" is a working name; collides with WAI-ARIA. (Revisit before public launch.)
- 2026-10-08 — Phase 0 defines only the 5 message types Phase 0 exercises (AuditEvent, PolicyRequest/Decision, UntrustedContent, ApplyTask, ActionPlan/Result); the other ten from PRODUCT_SPEC §4 are written by the phase that consumes them — defining fields no code reads is guessing. (Revisit per phase.)
- 2026-10-08 — S2 fields go through a repository (`aria_core/db/sensitive_profile.py`), not a SQLAlchemy type decorator — the AES-GCM associated data includes the row id, and a type decorator binds a value without knowing its destination row. An architecture test enforces that no other product module names an encrypted column, and that every such column is binary and declares its accessor.
- 2026-10-08 — `aria_migrate` gets an explicit RLS maintenance policy. `FORCE ROW LEVEL SECURITY` applies to the table owner, which would otherwise make backfills and verification impossible. Not a weakening: the migration role can drop the tables, so it was never a boundary — `aria_app` is, and owns nothing.
- 2026-10-08 — The migration role's DSN is kept out of the application's configuration entirely: no field on `Settings`, a separate `MigrationSettings` reading `.env.migrate`, and a start-up check that refuses to serve if `ARIA_MIGRATE_DATABASE_URL` is in the process environment. The migration role bypasses tenant isolation, so a request-serving process must not be able to reach it even in principle.
- 2026-10-08 — The free-text sensitive-pattern detector blocks at the LLM gateway and redacts in the audit log. Losing an audit event to a false positive is worse than storing a marker; sending a maybe to a third-party provider is worse than refusing. Blocked-S2 audit entries record the pattern name and that it was blocked, never the matched value.
- 2026-10-08 — Audit chain heads are anchored daily to an append-only store outside the database (`FileAnchorStore` in dev). The hash chain cannot detect a *consistent* rewrite — recompute every hash and it verifies — so detection needs something the database does not control. Production needs a store the application cannot rewrite at all (object storage with versioning + object lock, or a managed append-only log); until then anchors raise the cost of a silent rewrite rather than preventing it. (Revisit when the cloud is chosen.)
- 2026-10-08 — Pattern set for the sensitive-text detector is deliberately high-confidence only, and excludes a posting's sponsorship language ("we do not sponsor H-1B") — that is public S0 text the Answer Engine must read. Telling it apart from a candidate's own status needs the question classifier. (Revisit in Phase 4.)
- 2026-10-08 — Experience time is split into four disjoint buckets: full_time (salaried and contract), part_time (campus jobs, paid graduate/research assistantships), internship, and project (academic, personal, open source, unpaid research, volunteer). Every kind maps to exactly one bucket, so a summary can print all four without counting a month twice. Combining buckets unions the spans rather than adding the totals, because a part-time job can run during a research post.
- 2026-10-08 — "Years of experience" means full-time only by default. Internship months are included when the question explicitly includes them or the candidate sets `count_internships_as_experience`; part-time months when the question asks about part-time work or about work experience generally. Project months are never claimable. Rationale: a two-year assistantship at ten hours a week is not two years of experience, and a new grad who answers "2.6 years" on the strength of internships has overstated.
- 2026-10-08 — No candidate setting for part-time inclusion, deliberately asymmetric with internships. A setting is a standing preference about how to describe oneself; whether a campus job counts depends on what is being asked, so it stays question-driven rather than resolved by a checkbox set months earlier. (Revisit if real forms show a pattern.)
- 2026-10-08 — `RESEARCH` and `PART_TIME` overlap and the distinction is the candidate's: an unpaid lab rotation is research (project time), a paid assistantship is part-time (employment). ARIA never guesses — "were you paid for this?" is a fact about the person, not something a resume parser can read.
- 2026-10-08 — **Once a migration is committed it is never edited.** A schema change goes in a new migration, however small. Someone else's database has already run the committed file, so editing it produces two databases that both claim the same revision and differ. An uncommitted migration may still be amended, and the commit message says so. (Migration 0002 was amended twice while uncommitted, for the `count_internships_as_experience` column and the `part_time` kind.)
- 2026-10-08 — A pre-commit hook and a CI job fail on stray control characters in text files (`infra/checks/no_control_characters.py`). Twice a Windows path written through a shell heredoc turned `%APPDATA%\aria` into `%APPDATA%<BEL>ria`: the byte is invisible in a diff and in review, and the code silently used the wrong path. Byte-level checking is the only thing that catches that class of bug.
- 2026-10-08 — An undated **project** imports; an undated **role** does not. A role is a claim about time and `experiences.start_month` is NOT NULL, so a month ARIA invented would poison every years-of-experience figure. A project is a claim about work: "built a compiler for a course" is complete without dates, contributes zero project months, and its bullets import normally. Holding it back would lose real evidence to protect a number nobody was going to quote.
- 2026-10-08 — The unit-follows-number rule has one exception: a currency qualifier. `C$500K` and `US$1.2M` were rejected as identifiers because letters precede the digits, which is the right rule for `H100` and the wrong one for a currency symbol. The qualifier stays in the stored value, because restating `C$500K` as `$500K` changes the currency.
- 2026-10-08 — Extractor agreement means the two PDF readers are consistent, **not that either is right**. A real interleaved two-column PDF makes both flatten each visual row the same way ("EXPERIENCE EDUCATION" on one line), so agreement stays at 100% while the text is unusable. Merged columns therefore have their own detector — a line carrying two known section headings — and the question names the layout instead of asking what the "EXPERIENCE EDUCATION" section is. The truth rule held regardless: the importer recognised nothing and wrote nothing.
- 2026-10-08 — An education entry needs a school or a recognised degree. A stray `GPA: 3.8/4.0` on a fourth line used to become a row with no school and a degree of "GPA:" — a claim about nothing waiting in the approval queue. It now attaches to the degree above it; a line naming neither is reported as unparsed.
- 2026-10-08 — `user_questions` (migration 0003) is the table behind "ask, don't guess". `payload` carries what answering would create, because a role dated "Summer 2023" is not in the graph and an answer with nothing to attach to is useless. `dedupe_key` is unique per candidate so a re-import does not ask again — a queue that grows by five with every upload is one nobody reads, and that is the path that ends with an unreviewed draft on a resume. A CHECK requires an answered question to name who answered it and when.
- 2026-10-08 — **Answering a question applies the change, and the change still needs approving.** The held-back role arrives as a draft with its bullets; "were you paid?" sets the kind on a draft role. The answer and the claim stay two separate deliberate acts. An answer that does not answer the question (a season, a shrug, "maybe") is refused with what was expected, rather than stored — a stored shrug would close the question without resolving it, and the policy engine would then allow a submission that is still missing a date.
- 2026-10-08 — API authentication for Phase 1 is a single bearer token in `.env` that resolves to a configured user, tenant and candidate. It is not a placeholder for nothing: the token is required outside dev, the bind is restricted to loopback by a validator, and every action is audited against that user — an unauthenticated API would record every approval as nobody. Real sessions arrive with the Phase 6 dashboard; routes depend on `Caller`, not on a header, so that swap touches one module.
- 2026-10-08 — The CLI is an HTTP client over the API and never touches the database. Two code paths to the graph would mean "approve" could come to mean different things depending on who asked, and the CLI would bypass every check the API applies. Its tests assert wiring and output, never a rule — a copy of a rule here would be the start of a second implementation.
- 2026-10-08 — A refused upload is HTTP 200 with a reason, not a 4xx. The `uploads` row and its audit events are the product of ingestion even for a file that was turned away, and the client needs the row id to show the candidate what happened. A 4xx would be correct about the file and wrong about the request, which did exactly what it was asked.
- 2026-10-08 — Re-uploading byte-identical content returns the earlier upload rather than creating a second one or failing. Clicking upload twice is a thing people do; the unique index on `(candidate_id, sha256)` exists to recognise it, and before the route used it the second attempt reached the client as a 500. Nothing is reprocessed — parsing a PDF in a subprocess is the expensive part and the result is already on the row.
- 2026-10-08 — "Graph complete" is seven checks with written thresholds (`aria_api.routers.report`): one approved role, five approved facts, name/email/phone/city/region approved, one education entry, eight approved skills, no open questions, no uploads awaiting review. The thresholds are judgement calls and live in one place so they can be argued with; what is not a judgement call is that they are checked rather than felt. `aria report` exits non-zero when incomplete, so it is usable in a script.
- 2026-10-08 — Import is two layers: a pure parser that turns text into an `ImportPlan`, and one module (`importer/apply.py`) that writes the plan as drafts. The split means "what would importing this resume do?" is answerable without doing it, the parser is testable on strings, and there is exactly one place that touches the database. A plan has no status field at all, so it cannot express "approved".
- 2026-10-08 — A number is treated as a result only when something says what it measures: a unit, a currency symbol, a `+`, or a noun immediately after it. A dotted number with no unit is a version, a bare 4-digit number in 1900-2100 is a year, and letters anywhere in the token make it a name. That decidable test replaces a list of product names to maintain, and it is what rejects YOLO11m, Llama-3-8B, WCAG 2.1, GPT-4o, Python 3.12, v2.1, H100, S3, p95, a GPA and a phone number. **A unit follows a number and never precedes it** — the difference between `100h` and `H100`.
- 2026-10-08 — A date is read at the precision the resume wrote it. "Summer 2023" is a season and "2021-2023" is a pair of years; neither becomes a month. A role whose months cannot be read is still proposed but is **held back** from the graph with a question, and its bullets wait with it — a bullet approved without its role has no employer and no dates behind it. An end before its start is reported, never swapped.
- 2026-10-08 — A skill is only tagged from prose when the resume wrote it as a name (capitalised, upper case, or carrying a symbol or digit) if the term is five characters or fewer. A skill tag is evidence and evidence becomes months: "go to market" must not make the candidate a Go programmer. Terms in an explicit skills list are exempt, because the candidate wrote those down as skills.
- 2026-10-08 — Taxonomy implication edges are never followed on import. Next.js implies React, which helps *match* a requirement later; writing React onto the graph because the candidate wrote Next.js would be putting a word in their mouth.
- 2026-10-08 — Roles are deduplicated automatically on (employer, months) and facts never are. The same employer over the same months is the same job, and splitting it would double the calendar; which of two wordings of an achievement to keep is a judgement only the candidate can make, so the importer proposes a merge. **Two facts whose numbers differ are never duplicates** — "cut latency by 30%" and "by 60%" are one sentence apart and two different claims. A number set that is a subset of the other counts as agreement.
- 2026-10-08 — A bullet with fewer than three content words is never skipped as a duplicate. Containment is meaningless on one or two words, and a bullet dropped as a duplicate is one nobody reads again; below that threshold the importer proposes and asks.
- 2026-10-08 — A merged fact is rejected and kept, pointing at the survivor through `merged_into_fact_id`. Nothing is deleted: a resume built from the merged wording still has to explain itself, and an import must not re-propose a wording already set aside. A fact matching a *rejected* one is never proposed again, which is what the rejected state is for.
- 2026-10-08 — A street address found in a resume header is discarded and the drop is reported. There is no `ProfileFieldKind` for one and nothing in the product needs it; a header that carries one keeps its city and region. Telling the candidate what was dropped matters as much as dropping it — an importer that quietly discards part of a line is indistinguishable from one with a bug.
- 2026-10-08 — The importer reports everything it could not do: an unrecognised heading (whose lines are not imported), an unparsed block, a term the taxonomy lacks, a date it could not read, a line it dropped. A resume importer that reports only its successes is lying by omission about a document the candidate is about to approve.
- 2026-10-08 — A plain-text notes file is read as a list of skills and **produces no facts**. A note saying "I know Python" does not say what was built with it, and a declared skill is not evidence. A line with no separator that resolves to nothing is the candidate's own group heading, not a taxonomy gap — reporting "Frontend" as a missing skill buries the real ones.
- 2026-10-08 — `aria_core.documents` owns `LINKS_HEADING` and the function that splits the block off. The document parser writes it and the importer reads it back; defining it in either would leave the other matching on a string it does not own, and a heading that drifts by one character turns a LinkedIn URL into a resume bullet.
- 2026-10-08 — A profile field is re-proposed only when its value has changed. Two resumes carry the same name and email, and a queue full of decisions already made is a queue that stops being read — which is how an unreviewed draft eventually reaches a resume. A different value for the same kind is still proposed, because a newer phone number is news.
- 2026-10-08 — Non-ASCII characters in the importer's code string literals are written as `\uXXXX` escapes, while docstrings keep real punctuation. In a character class an en dash and a hyphen are indistinguishable by eye and mean different things — the same class of bug as the BEL byte the control-character check now catches. (It caught a literal backspace byte in a theme pattern during this work, which had silently disabled every theme.)
- 2026-10-08 — Uploads accept PDF and plain text only; .docx is recognised and declined. A .docx is a zip of XML, which brings XXE, zip bombs and external relationships, and every tool that writes one also writes a PDF — the attack surface buys very little. The reader and its tests stay built behind `ARIA_ALLOW_DOCX_UPLOADS`, which defaults false, so turning it back on is a configuration change rather than a rebuild. The refusal names what the file actually is and says to use Save As → PDF. (Revisit at beta if users ask.)
- 2026-10-08 — PDF link annotations are extracted as plain-text data and appended under a labelled heading, so a candidate's LinkedIn and GitHub URLs survive — they live in annotations, not the text layer, and extracting text alone loses them. Only http, https and mailto are kept; javascript, file, data and ftp are dropped. **Nothing is ever fetched**: a URI from an uploaded file is untrusted input, and following one would make the parser a request-forgery tool on behalf of whoever sent the file.
- 2026-10-08 — pypdf is the source of truth for PDF text, always, with one stated exception: if pypdf finds no usable text layer and pdfminer does, pdfminer's text is used. The chosen extractor is recorded on the upload (`extractor=…` in `parse_detail`). The previous rule — whichever output was longer — was deterministic but arbitrary, and could flip between two runs of the same file.
- 2026-10-08 — Pages where the two extractors disagree are flagged for the candidate's review rather than resolved by guessing. A two-column layout can come out interleaved and nothing tells us which order was intended; the text is still imported, `uploads.needs_review` is set, and the detail names the pages to check against the original. Guessing silently is how a resume ends up saying something the candidate never wrote.
- 2026-10-09 — Every graph row that can be approved records **who approved it** (migration 0004 adds `approved_by` to experiences, projects, education, profile_fields, declared_skills, achievements and motivations; `facts` always had it). Approving "I worked at Accenture from June 2024" is as much a truth claim as approving a bullet. A CHECK enforces it: an approved row with no approver and no timestamp is rejected by the database, because the alternative is every future writer remembering and the first one to forget produces a claim with nobody attached. `ON DELETE SET NULL`, so removing a user does not remove the history of what they approved.
- 2026-10-09 — `aria_core.graph.entities` approves the seven non-fact graph tables, using **the same transition table as facts** (`ALLOWED_ACTIONS`) rather than a copy, because "approved" has to mean the same thing everywhere. Facts keep their own module: immutable revisions, a merge operation, and an architecture test that fails if anything else reads them. This closed a real hole — the completeness report counted approved roles, education, skills and contact details, and nothing could approve any of them, so the Phase 1 gate was unreachable. A gate that cannot be passed teaches you to ignore the report.
- 2026-10-09 — `audit_events.tenant_id` is deliberately **not** a foreign key, now documented on the model. Every other tenant-scoped table cascades from `tenants`, so deleting a tenant erases its data; an audit log that vanished with it would record nothing about the one action most worth recording. Confirmed by observation: dropping 20 demo tenants left 11,182 audit events intact.
- 2026-10-09 — `seed-me` treats **configuration as the source of truth**, not the email address. Once `.env` names an identity it verifies and prints it and creates nothing; it refuses outright when the named candidate is missing or belongs to another user. The previous version claimed to be idempotent by email and was not — `users` is unique on `(tenant_id, email)` rather than on `email`, and a platform-scoped transaction cannot read tenant rows at all, so the lookup matched nothing and every run created another identity. Finding a user by email would mean searching every tenant for an address, which is the one thing row-level security exists to prevent.
- 2026-10-09 — The CLI reads the API token and URL from `.env` when the environment does not set them, with the environment still winning. One machine, one file: having the CLI ignore the file the API already reads meant exporting a variable that was written down three feet away. A missing or half-written `.env` is not an error for the CLI, which needs no database URL.
- 2026-10-09 — Columns are detected **geometrically**, from pdfminer's text-box x-coordinates: a gutter is a vertical band of x values that no text crosses. The text heuristic it replaces (two known section headings on one line) caught "EXPERIENCE EDUCATION" and missed the common case — a sidebar of skills beside a column of bullets, where every merged row reads plausibly and nothing in the words gives it away. The heuristic stays as the fallback for inputs with no geometry: a `.txt` upload flattened before ARIA saw it, and a PDF whose layout analysis failed.
- 2026-10-09 — A page whose columns the geometry resolves is **rebuilt in reading order** (spanning header, left column, right column, spanning footer) and flagged for review. The gutter settles which column comes first; it does not settle whether a sidebar of skills belongs where it landed. The page is recorded in `uploads.parse_detail` with the gutter's coordinates and in `column_pages`, and `extractor` becomes `pypdf+layout` — pypdf's reading order for such a page is known to be wrong, because it follows the content stream, which crosses the gutter a visual row at a time.
- 2026-10-09 — Where the geometry sees columns and cannot order them, the upload is **refused** with that reason: three or more columns, or something spanning both columns part-way down the page. Reading columns the wrong way round attaches the wrong dates and the wrong employer to the wrong work, so there is no guess worth making. A banner that does not actually reach across the gutter is left-column content, not an ambiguity — refusing there would be superstition about a layout that is in fact resolvable.
- 2026-10-09 — **No text box may be dropped.** Every box must land in a column or span the gutter; a page where one does not is treated as ambiguous. This was a real bug: an early version set aside boxes wider than 85% of the widest box to stop a spanning title hiding the gutter, which moved the gutter into the middle of the left column's longest lines and silently lost three bullets. Text the candidate wrote disappearing with nothing reported is this parser's worst failure mode.
- 2026-10-09 — **Agreement between the two PDF extractors means they are consistent, not that either is correct**, recorded in RESUME_ENGINE §8 because the Phase 2 ATS validator depends on the same cross-check. They share a failure mode: on a multi-column page both flatten each visual row identically, so the check reports 100% agreement on unusable text. Disagreement proves something is wrong; agreement proves nothing. Reading order is therefore verified geometrically, and the Phase 2 validator reuses `aria_document_parser.layout` pointed at ARIA's own rendered output.
- 2026-10-09 — Onboarding interview questions come from **written templates**, not from a model. A question is a prompt for a claim — "do you know how many teams used them?" invites a number that ends up on a resume — so the wording was chosen by a person and can be argued with in review. Templates also mean the same graph always produces the same questions, and nothing untrusted reaches an instruction because nothing is generated. Every template carries a `why`, because "why are you asking me this?" deserves an answer and a visible purpose gets a better answer.
- 2026-10-09 — Enrichment answers become **new draft facts beside the originals**, never edits of them (RESUME_ENGINE §5). Rewriting the bullet that was asked about would mean a sentence typed into a prompt silently replacing one the candidate had already approved. The answer runs through the same metric and skill extraction as an imported bullet, and the skill the question was about counts as evidence even when the answer does not spell it out again — "I used it for the event pipeline" is an answer about Kafka.
- 2026-10-09 — The enrichment interview finds every gap and asks about **at most eight at a time**. A graph with thirty numberless bullets would otherwise produce thirty questions in one round, and a queue of thirty is a queue nobody answers — which leaves the graph exactly as incomplete as before. Skipped gaps are found again next round; gaps are ordered so that a role with no achievements under it is asked about before a fifth bullet without a number. Finding gaps is a separate read-only operation from asking about them, so a report can show what is missing without filling anybody's queue.
- 2026-10-09 — A listed skill counts as evidenced by a **draft** fact, not only an approved one. The gap is filled the moment the draft exists; asking again because it has not been approved yet would be asking about something the candidate has already done.
- 2026-10-09 — The motivations interview is six fixed questions, the same for everybody, and nothing is ever inferred from the resume. What somebody has done and what they want to do next are different things, and inferring the second from the first is how a cover letter ends up enthusiastic about work the candidate was trying to leave. Answers are stored verbatim: a motivation is the one claim that cannot be checked against a fact, so it is the candidate's words or nothing.
- 2026-10-11 — Resume intake parses **document geometry** (`pdfplumber` chars: bbox, font name, size, with weight inferred per §5.1), never `extract_text()` output — content-stream order is generator-dependent and meaningless. Reading order is reconstructed by column detection + y/x sort. This is what makes two-column templates (a large share of real resumes) and float-reordered PDFs parse correctly. (RESUME_ENGINE §5)
- 2026-10-11 — New-bullet vs wrapped-line is decided by **hanging-indent geometry**, not by the presence of a marker glyph — CSS `list-style` markers never reach the text layer, so a glyph-only rule fails on a whole class of documents.
- 2026-10-11 — Intake **refuses rather than guesses**: per-entry shape rules plus document-level gates return `needs_user_fix` and write nothing. A fabricated entry is worse than a missing one; false-entry rate must be 0. Prompted by an import that invented 9 roles from wrapped bullet fragments and reported `agreement 100%`.
- 2026-10-11 — Cross-extractor **agreement is a diagnostic, never a confidence score** and is never shown to the user as a percentage. Two extractors reading the same wrong order agree perfectly.
- 2026-10-11 — Intake always produces drafts for user approval, even at maximum confidence — "ask, don't guess" applied to onboarding, and the backstop behind every parser rule.
- 2026-10-11 — PDF is one intake path among several (paste text, .docx, manual/interview, LinkedIn export); `.docx` is preferred when available because it carries real structure.
- 2026-10-11 — Generated resumes are round-tripped through our own Stage 0 parser in the ATS check; template lint bans `float` date columns, CSS list markers, styled contact-line inlines and ligatures. (RESUME_ENGINE §10)
- 2026-10-11 — **PyMuPDF is banned from the codebase** — it is AGPL-3.0 or paid-commercial, and AGPL §13 would oblige offering source to every user of a hosted ARIA. Stage 0 uses `pdfplumber` (MIT) for character geometry and `pypdf` (BSD-3) for the independent cross-check; `pdfminer.six` (MIT) and `pypdfium2` (Apache-2.0/BSD-3) are also acceptable. Every new PDF dependency is license-checked before it is added. (RESUME_ENGINE §5.1)
- 2026-10-11 — Intake fixtures carry a synthetic identity, not the founder's real contact details — git history is permanent and the corpus should stay shareable with collaborators or as open source. Layout pathologies are what the fixtures test; the name on them is irrelevant.
- 2026-10-11 — The §5.6 cross-extractor disagreement fixture is `float_scrambled.pdf`, not `per_glyph_contact.pdf`. On the pinned `pypdf` (6.19.0) the per-glyph contact line extracts intact, so it cannot exercise a disagreement; the per-character split seen earlier came from `pypdf` 3.x. `per_glyph_contact.pdf` becomes a baseline-equivalence fixture. §5.3's rule — rebuild word boundaries from character gaps, never trust an extractor's word grouping — stands, justified by extractor behaviour varying between versions rather than by any one extractor being broken. (RESUME_ENGINE §5.3, fixtures README)
